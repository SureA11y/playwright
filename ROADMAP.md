## 1. What this is and why it's a separate project

`a11y-core` is the DOM-rules accessibility engine, living at `../a11y-core` (a sibling directory, not a parent — this is a separate git repo and a separate npm package). This project is a thin Playwright-specific binding around it: it drives a real browser page, injects the engine, and returns results in a builder API modeled on axe-core's `AxeBuilder` for migration familiarity.

**Why a separate project instead of a monorepo subfolder of `a11y-core`** (decided 2026-07-22): matches how axe-core itself ships (`axe-core` core package + separate `@axe-core/playwright`/`@axe-core/puppeteer` binding packages); keeps `a11y-core` a pure engine dependency with no browser-automation-framework tooling bleeding into its own `package.json`; avoids introducing monorepo tooling (npm workspaces, etc.) into a repo that has none today; allows independent versioning/release cadence once both are published. The one real cost is coordination: since `a11y-core` isn't published, this project depends on it via `"a11y-core": "file:../a11y-core"` in `package.json` — if you move this project, update that path (or once `a11y-core` is published to npm, switch to a real version range and drop the relative dependency entirely).

**Why Playwright first, not Puppeteer/Cypress/WebdriverIO too**: only Playwright's injection mechanics have actually been proven working (`page.evaluate(fn, singleArgObject)`, single-arg only — confirmed empirically against a real Playwright page, see `src/A11yCoreBuilder.js`'s own header comment and `../a11y-core/docs/INTEGRATION.md`). Puppeteer's `page.evaluate` is genuinely variadic (different enough that copying this file wouldn't be a straight port), and Cypress doesn't drive a page via evaluate at all (it runs inside the same browser as the app under test, injection would go through `cy.window()`/a custom command — a different execution model entirely). A generic multi-framework scaffold was considered and deliberately rejected (2026-07-22) as premature abstraction for a need that was just "one Playwright project" — if/when a second framework binding is wanted, treat it as its own new project informed by this one's structure, not a generator invocation.

## 2. Current status (2026-07-22)

**Built and verified**: `src/A11yCoreBuilder.js` — a fluent builder (`include`, `exclude`, `withTags`, `disableTags`, `withRules`, `disableRules`, `options`, `withCustomRules`, `frames`, `reportOnly`, `elementRef`, `analyze`) wrapping the same single-arg-wrapper injection pattern already proven in `a11y-core`'s own live-DOM cross-engine tooling (`a11y-core/scripts/cross-engine/adapters/a11ycore-live-adapter.js`). 40 tests in `tests/builder.test.js`, all run against real Chromium pages (except `reportOnly()`'s invalid-outcome check and `withCustomRules()`'s four validation-error checks, none of which need a browser), covering:

- Single-method behavior: basic scan, `include()` scoping, `include()` called twice (multi-region union), `exclude()`, `disableRules()`, `withRules()`, `disableTags()`, `withTags()`, `options()` (verified the option actually reached the engine via the result's own echoed `engineOptions`, not just presence of a result).
- **Combinations** (added in the 2026-07-22 audit pass, see the "Last updated" note above): `include()`+`exclude()` together (scoped to a region minus a sub-part of it); `withRules()`+`disableRules()` on the same ID (disable wins); `withTags()`+`disableTags()` on the same tag (disable wins, empty result); `withRules()`+`withTags()` together (a11y-core's default `includeMode: 'and'` — a rule must satisfy *both*, not either, which is non-obvious enough to be worth its own test); `options({ customRules })` combined with both `frames(true)` (the custom rule runs in every frame) and `reportOnly()` (filtered the same as a built-in rule); `reportOnly()`+`elementRef(true)` together (surviving occurrences still carry a usable handle).
- `frames(true)` three ways -- no sub-frames (`{ topFrame, frames: [] }` shape), a same-document `srcdoc` sub-frame (findings correctly kept separate from the top frame's, not merged/double-counted), and a genuinely cross-origin sub-frame (`https://example.org/`, the same page used to verify the underlying claim in gap #1 below -- the one test here with a real network dependency, deliberately, since that's exactly the scenario being proven).
- `reportOnly()`: filtering down to `['fail']` only, rejecting an invalid outcome string, and applying independently per-frame when combined with `frames(true)`.
- `elementRef()`: a real, usable `ElementHandle` proven by reading a live DOM property through it, an occurrence with an empty selector (no single target element) leaving `elementHandle: null` rather than throwing, and resolving against each frame's own document when combined with `frames(true)`.
- `options({ customRules })`: registers a runtime custom rule via a11y-core's `engineOptions.customRules` escape hatch -- confirmed the occurrence gets the same automatic `selector`/`structuralPath` fill-in a built-in rule's does. Superseded as the recommended path by the dedicated `.withCustomRules([...])` method (see §3 item 4), which still composes with this raw form if both are used together.
- **Mutability** (added in the 2026-07-22 second audit pass, see the "Last updated" note): reusing one instance across two `.analyze()` calls with a scoping method called again in between accumulates rather than resets; `.reportOnly()`/`.frames()`/`.elementRef()` overwrite instead. Both directions now locked down with a test each.

Also built: `src/A11yCoreBuilder.d.ts` (re-exported via `src/index.d.ts`, wired up through `package.json`'s `types` field) — hand-written types for the whole builder API and a11y-core's native result shapes, mirrored from `../a11y-core/docs/OUTPUT_SCHEMA.md`. `playwright` moved to also being a `peerDependencies` entry (was `devDependencies`-only) since consumers need it installed for the types (`Page`, `ElementHandle`) to resolve. Verified with a real standalone `tsc --strict` compile against a small consumer script exercising every builder method and both `analyze()` return shapes — not just "the file parses."

Also built: `examples/playwright-test-example.spec.js` (`npm run example:e2e`) — the pattern that actually matters for an E2E suite (a real `@playwright/test` test using `A11yCoreBuilder` as an accessibility gate via `expect(results.checksResults).toEqual([])`), as opposed to `basic-scan.js`'s standalone-script usage. Verified by actually running it with `npx playwright test`, not just reading it: one test proves a page with real violations (unlabeled `<button>`, `<img>` missing `alt`) gets caught, one proves a well-formed page passes cleanly with `toEqual([])`. Confirmed it doesn't collide with `tests/builder.test.js` (`npm test`'s glob is scoped to `tests/**/*.test.js`, so the two runners -- `node --test` and `playwright test` -- never see each other's files).

Also built: `src/formatFailures.js` (exported from `src/index.js`, typed in `src/A11yCoreBuilder.d.ts`) — takes a `checksResults` array and returns a short readable block, one numbered entry per occurrence (`ruleId (severity): summary`, then `at <selector>` and the `hint`, on their own lines), defaulting to `fail`/`cantTell` outcomes (the only two that ever carry occurrences) with an `{ outcomes: [...] }` override. Handles the one real edge case in `OUTPUT_SCHEMA.md`'s own notes: a thrown rule (`occurrences: []`, `error` set) is surfaced via its `error` message instead of silently vanishing from the report. Verified against a real failing test (`npx playwright test`) that the formatted block prints at the top of the failure output, ahead of Playwright's own unavoidable raw `toEqual` diff underneath -- not just reasoned about. Deliberately exported as a plain function rather than a custom `expect` matcher (no `expect.extend()`): keeps it usable from any assertion library, matching this project's existing test-runner-agnostic stance (see `examples/playwright-test-example.spec.js`'s own note on `playwright/test` vs `@playwright/test`). 6 tests in `tests/formatFailures.test.js`: no-violations message, single-occurrence formatting, numbering across multiple rules/occurrences, ignoring `pass`/`notApplicable` and respecting a custom `outcomes` filter, surfacing a thrown rule via `error`, and one full integration test against a real scan's `checksResults`.

Also built: `LICENSE` (MIT, mirroring `a11y-core`'s own) — `package.json` declared `"license": "MIT"` since the initial commit with no actual license file backing that claim.

Also built: `tests/cross-browser.test.js` — 2 tests proving the injection mechanism (`page.evaluate(wrapperFn, singleArgObject)`) works against Firefox and WebKit, not just Chromium, which every other test in this suite exclusively launches. This project calls itself a "Playwright binding," which implies all three engines Playwright drives, not just one -- that claim had never actually been checked before this. Requires `npx playwright install firefox webkit` locally (see `README.md`'s install section, which previously didn't mention `npx playwright install` at all -- not even for Chromium, which every existing test already silently depended on).

**Not yet built**: everything else. This is a working v1 skeleton, not a finished package — no CI, no npm publish setup, no version pinning strategy against `a11y-core` once that's published (both explicitly deprioritized for now, see §4).

**Watch item, not urgent (noted 2026-07-22)**: `a11y-core`'s `src/core.js` grew from ~1.86MB to ~3.1MB in a single day, as a side effect of adding `runa11yCoreAcrossFrames`/`a11yCoreEnableFrameResponder` (cross-frame scanning for a11y-core's own no-automation-driver use case) — each needed its own private, fully self-contained copy of the entire rule catalog to stay bundler-free, the same trick `runa11yCoreInPage` already used, tripling the number of embedded catalog copies in the file. Doesn't affect this project's actual browser payload (`analyze()` only ever injects `runa11yCoreInPage.toString()` via `page.evaluate`, and that function's own body didn't change size), but since `node_modules/a11y-core` is symlinked to the live sibling repo, `require('a11y-core')` on the Node side now loads the full 3.1MB into this process instead of 1.86MB. Worth tracking because `a11y-core`'s repo is already close to Bitbucket's 1GB workspace warning. If it becomes a real problem, the fix is on `a11y-core`'s side (drop the bundler-free requirement for those two cross-frame functions specifically), not something to work around here.

## 3. Known gaps vs. axe-core (prioritized, carried over from `a11y-core`'s own scoping pass)

`a11y-core`'s `ROADMAP.md` §7 item 8 has the full reasoning behind each of these (found 2026-07-22 by reading axe-core's actual `axe.d.ts`, not assumed from memory) — read that for the deeper "why," this is the condensed pointer so it's not lost if this project is ever opened without that context handy.

1. **Cross-frame/iframe scanning -- built and verified 2026-07-22.** Originally scoped as engine-blocked by analogy with axe-core, which needs a real postMessage-based protocol (`runPartial`/`finishRun`/`frameMessenger`) to reach cross-origin iframes -- because axe is injected as a plain `<script>`, fully subject to the browser's same-origin policy. That reasoning turned out not to transfer here: Playwright drives every frame via CDP at the automation-process level, not as in-page script, so it isn't subject to that restriction at all. Verified empirically (real Chromium run, a page with a genuinely cross-origin iframe, `https://example.org/`): `frame.evaluate()` on that cross-origin frame works with zero restrictions, and running the *full* `runa11yCoreInPage` inside it via the same single-arg-wrapper pattern `analyze()` already uses (125 rules, correct results, zero errors) required no engine changes whatsoever. Real pages do put real content in frames (cookie-consent dialogs, payment widgets) -- this isn't hypothetical, it's already been hit once this session (BBC News' cookie dialog, see `a11y-core`'s `ROADMAP.md`).

   **Built as**: `src/A11yCoreBuilder.js`'s `.frames(true)` — default off (so plain `.analyze()` is unchanged), and when enabled, iterates `this._page.frames()` and runs the existing wrapper-injection mechanism once per frame (no new injection logic, just a loop over the same `runInFrame` helper `analyze()` itself uses for the top frame). Returns `{ topFrame, frames: [...] }` (frame-qualified, not flattened into one list, since a finding's `selector` is only meaningful within its own frame's document) rather than the single native result object `.analyze()` returns without `.frames(true)`. A frame that errors mid-scan (detached, navigated away, or a sandboxed frame the browser blocks scripting in) is reported as `{ url, error }` in the `frames` array rather than aborting the whole multi-frame scan. 3 new tests: no sub-frames, a same-document `srcdoc` sub-frame (confirms findings are kept separate per frame, not merged/double-counted), and a genuinely cross-origin sub-frame (`https://example.org/`).

   **Left as an open, non-blocking judgment call** (not something that needs an engine answer, since `a11y-core` already documents itself as "returns data, not a verdict" — see its `docs/INTEGRATION.md`): page-global rules (`page-title-present`, `meta-refresh-*`, etc.) run once per frame too, same as every other rule — whether a sub-frame's own "page title" finding is noise or a legitimate separate concern for that embedded document is left to the consumer to interpret or filter, not decided here.
2. **Element references in results -- built and verified 2026-07-22.** (`elementRef`-equivalent). Axe can return the actual DOM element alongside the selector string.

   **Built as**: `src/A11yCoreBuilder.js`'s `.elementRef(true)` — default off (a handle per occurrence is a real page query, costing more than a plain `.analyze()`). When enabled, a `_attachElementRefs()` helper runs after each frame's `evaluate()` call, resolving every fail/cantTell occurrence's `selector` via `<page-or-frame>.$()` (plain `ElementHandle`, not `evaluateHandle` -- no extra in-page wrapper needed) and attaching it as `occurrence.elementHandle`. Uses whichever `frameOrPage` actually ran that portion of the scan, so it composes correctly with `.frames(true)` without extra plumbing -- a sub-frame's occurrences resolve against that sub-frame's own document, not the top page's, since `runInFrame` already had the right frame reference in scope for the injection itself. **Real edge case caught while building this** (not hypothetical, hit by the test suite's own second `elementRef` test): not every occurrence has a single target element -- e.g. `a11ycore-contrast-enhanced` can report a page-wide occurrence with `selector: ""`, and calling `.$("")` on that throws (`""` isn't a valid CSS selector). Fixed by checking `occurrence.selector` truthiness before calling `.$()`, leaving `elementHandle: null` for that case rather than crashing the whole scan. 3 new tests: a real usable handle (proven by reading a live DOM property through it, not just checking truthiness), the empty-selector case resolving to `null` instead of throwing, and per-frame resolution when combined with `frames(true)`.
3. **Result verbosity control -- built and verified 2026-07-22.** (axe's `reporter: 'no-passes'` equivalent). `a11y-core`'s `checksResults` always includes every rule's outcome, including `pass`/`notApplicable` — a deliberate engine design choice, not something to change there.

   **Built as**: `src/A11yCoreBuilder.js`'s `.reportOnly(['fail', 'cantTell'])` — validates each outcome against a11y-core's own valid set (`pass`/`fail`/`cantTell`/`notApplicable`, throwing on anything else) and, in `analyze()`, filters `checksResults` down to just those outcomes via a small `_applyReportOnly()` helper. Pure post-filter, binding-layer only — `a11y-core` still computes every rule regardless, this just trims the payload handed back. Applied through the same helper whether or not `.frames(true)` is combined in — called on `topFrame` and each `frames[i]` independently, since `checksResults` lives one level deeper in that shape (a frame that errored mid-scan, `{ url, error }`, has no `checksResults` and passes through the helper unchanged rather than throwing). 3 new tests: filtering to `['fail']` only on a simple page, rejecting an invalid outcome string (no browser needed for that one), and confirming the filter applies independently per-frame.
4. **Runtime custom-rule registration -- built and verified 2026-07-22.** `a11y-core` supports `engineOptions.customRules` (see its `docs/ENGINE_OPTIONS.md` and `ROADMAP.md` §7 item 8): a descriptor in the same shape as an internal rule module (`{ id, meta, runInPage, applicability?, data? }`), registered per-scan (not added to any persistent catalog). `runInPage`/`applicability` accept a real function or a function-source string — the string form exists *specifically* for this binding's situation: a Playwright `page.evaluate(runa11yCoreInPage, { engineOptions })` call serializes `engineOptions` through a JSON boundary that cannot carry a live function, so a caller here needs to pass `fn.toString()` rather than `fn` itself.

   **Built as**: `src/A11yCoreBuilder.js`'s `.withCustomRules([...])` — accumulates (like `.withRules()`/`.withTags()`), validates each descriptor's `id`/`runInPage`/`applicability` synchronously (throwing immediately on a missing `id` or a `runInPage`/`applicability` that's neither a function nor a non-empty string, rather than letting a11y-core's own engine-side silent-skip behavior swallow a programmer error deep inside the page) as one all-or-nothing batch before registering any of it, and merges into `engineOptions.customRules` at `analyze()` time, concatenated with (not clobbering) anything already set via a raw `.options({ customRules })` call so both ways of registering compose.

   **Real bug caught while building this, not hypothetical**: a live function passed as `runInPage`/`applicability` needs converting to a function-source string for the reasons above, and the naive `fn.toString()` breaks for the single most idiomatic way to write one of these descriptors — ES6 method-shorthand (`{ runInPage(ctx) { ... } }`, what every example in this project's own docs/tests uses). `Function.prototype.toString()` on a method-shorthand property omits the `function` keyword entirely, so a11y-core's own revival mechanism (`new Function('return (' + value + ')')()`) can't parse it back as a standalone expression — the rule would silently vanish from `checksResults` with no error anywhere, exactly the kind of silent failure `.withCustomRules()` exists to prevent. Fixed by actually attempting the reconstruction locally, in Node, the same way a11y-core will on the page side, before ever crossing the `page.evaluate()` boundary — patching in the missing `function` keyword only when the direct `.toString()` doesn't already work, rather than guessing at the syntax with a regex.

   12 new tests in `tests/builder.test.js`: basic registration via a live method-shorthand function (the exact case that exposed the bug above), array form (multiple rules in one call), accumulation across repeated calls, composing with a raw `.options({ customRules })` call, combined with `.frames(true)` and `.reportOnly()`, a live `applicability` function (both true/false paths), an already-stringified `runInPage` (back-compat with the raw-passthrough form), and four validation-error cases including atomicity (one invalid descriptor in an array registers none of it, not a partial batch).

   README's "Registering a custom rule at runtime" section and this file's `.d.ts` (`CustomRuleDescriptor`) now document `.withCustomRules()` as the primary path; the raw `.options({ customRules })` passthrough is still mentioned and still works, composing with the new method rather than being replaced by it.
5. **xpath/ancestry addressing -- turned out to already be resolved, discovered 2026-07-22.** Axe can report a finding's location as CSS selector, xpath, or a structural-path array. This was scoped as blocked on `a11y-core` exposing its internal `structuralPath` utility on public per-occurrence output — checking a real scan's output while building the TypeScript types (§2) showed `occurrences[i].structuralPath: number[] | null` is already present (`a11y-core`'s own `docs/OUTPUT_SCHEMA.md` documents it too, e.g. `[1, 0]` for a top-level `<img>`). Since this binding passes occurrences through unreshaped, that field was already reaching consumers with zero code change here — the note above claiming otherwise was stale (`a11y-core` must have added it after this note was originally written). Added to this binding's own `.d.ts` types as part of this discovery.

## 4. Immediate next steps (pick up here)
